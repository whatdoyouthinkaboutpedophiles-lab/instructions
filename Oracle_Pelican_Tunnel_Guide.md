# Инструкция: Управление портами и туннелем (Oracle ↔ Pelican)

## Базовый принцип работы
Сеть между серверами функционирует на основе маршрутизации по условиям (Policy-Based Routing):
1. Сервер Oracle принимает входящий пакет из интернета и перенаправляет его в VPN-туннель (на IP-адрес `10.0.0.2`).
2. Пакет поступает в Docker-контейнер на домашнем сервере.
3. Домашний сервер формирует ответ. Для корректной маршрутизации обратно через туннель (чтобы пакет не ушел в обычную локальную сеть), этому ответу присваивается специальная метка (`MARK 100`).
4. Таблица маршрутизации фиксирует пакет с меткой `100` и принудительно отправляет его обратно в туннель к серверу Oracle.

## Часть 1. Алгоритм добавления нового порта
При установке новых плагинов или запуске серверов может потребоваться открытие дополнительных портов (в качестве примера рассмотрим настройку для TCP `28085`).

### Шаг 1. Настройка сетевых правил (Сайт Oracle Cloud)
1. Авторизуйтесь в панели управления Oracle Cloud.
2. Перейдите в раздел **Virtual Cloud Networks** -> **[Имя вашей сети]** -> **Security Lists**.
3. Добавьте новое правило для входящего трафика (**Ingress Rule**):
   - **Source**: `0.0.0.0/0`
   - **Protocol**: `TCP` (или `UDP`, в зависимости от требований приложения)
   - **Destination Port**: `28085`

### Шаг 2. Проброс пакетов в туннель (Консоль Oracle)
Подключитесь к серверу Oracle по SSH и выполните следующие команды:

```bash
# 1. Проброс трафика на домашний сервер (DNAT)
sudo iptables -t nat -I PREROUTING 1 -p tcp --dport 28085 -j DNAT --to-destination 10.0.0.2:28085

# 2. Разрешение на прохождение пакета (FORWARD)
sudo iptables -I FORWARD 1 -p tcp --dport 28085 -j ACCEPT
```
*(При необходимости замените `tcp` на `udp`).*

### Шаг 3. Маршрутизация ответов (Консоль сервера Pelican)
Подключитесь к домашнему серверу по SSH и промаркируйте ответы, отправляемые с нового порта:

```bash
sudo iptables -t mangle -I PREROUTING -p tcp --sport 28085 -j MARK --set-mark 100
sudo iptables -t mangle -I OUTPUT -p tcp --sport 28085 -j MARK --set-mark 100
```
*(Внимание: здесь используется параметр `--sport` (source port), поскольку маркировке подлежит трафик, исходящий с данного порта наружу).*

### Шаг 4. Настройка панели (Браузер Pelican)
1. В веб-панели управления перейдите в настройки целевого сервера: **Admin Area** -> **Servers** -> **[Требуемый сервер]** -> вкладка **Build Configuration**.
2. Увеличьте значение **Allocated Ports**, чтобы разрешить контейнеру Docker использовать еще один порт. Завершите действие нажатием **Update**.
3. Вернитесь в стандартный режим просмотра сервера -> **Network**, и привяжите порт `28085` к IP `10.0.0.2`.
4. Перезапустите сервер.

## Часть 2. Мониторинг текущих правил и открытых портов
Для диагностики и проверки активных маршрутов в туннеле используются следующие команды:

### 1. Проверка входящих соединений на стороне Oracle
Запрашивает список портов, перенаправляемых в туннель на `10.0.0.2` (выполняется на Oracle VPS):
```bash
sudo iptables -t nat -S PREROUTING | grep DNAT
```

### 2. Проверка маркировки ответов на стороне Pelican
Показывает все порты, трафику которых присваивается метка `100` (выполняется на домашнем сервере Pelican):
```bash
sudo iptables -t mangle -S | grep "MARK --set-xmark 0x64"
```
*(Значение `0x64` — это шестнадцатеричное представление числа `100`).*

### 3. Проверка прослушиваемых портов (Docker)
Отображает реально открытые порты на интерфейсе туннеля (выполняется на домашнем сервере Pelican):
```bash
sudo netstat -tulpn | grep 10.0.0.2
```
*Если требуемый порт отсутствует в списке, это означает, что панель Pelican не пробросила его из контейнера. В таком случае рекомендуется проверить настройки лимитов в разделе Build Configuration.*

## Часть 3. Правила безопасности локальной сети
Локальные сервисы, такие как AdGuard (порт `8080`), веб-интерфейс Pelican панель (`8081`) и Wings (`8085`), функционируют стабильно благодаря тому, что их трафик не маршрутизируется в туннель. Во избежание сбоев в работе локальной сети необходимо соблюдать три обязательных правила.

### Правило 1. Не маркировать служебные порты панели
Команды маркировки (`MARK 100`), описанные в "Шаге 3", следует применять исключительно к игровым или рабочим портам контейнеров (например, `28015`, `28082`, `27017` и т.д.).
Категорически не рекомендуется выполнять команды вида `sudo iptables -t mangle... --sport 8081 -j MARK --set-mark 100`, так как это приведет к потере доступа к панели Pelican из локальной сети.

### Правило 2. Разделение исходящего трафика
При необходимости перенаправления в туннель любого нестандартного исходящего трафика (например, запросов по портам `80` и `443` для связи Rust+ с серверами Facepunch или обращения к внешним БД), всегда следует указывать исключение для локальной подсети: `! -d 192.168.0.0/16`.

Пример корректной команды перехвата исходящего трафика:
```bash
sudo iptables -t mangle -I PREROUTING -p tcp --dport 443 ! -d 192.168.0.0/16 -j MARK --set-mark 100
```
*Эта мера предотвратит ошибочную отправку локальных запросов (например, к AdGuard) в VPN-туннель.*

### Правило 3. Обязательное сохранение правил
Все внесенные изменения в правила `iptables` сбрасываются после перезагрузки систем.
Для применения настроек на постоянной основе, необходимо убедиться, что на серверах установлен пакет `iptables-persistent`.

Для сохранения конфигурации выполните на **обоих** серверах:
```bash
sudo netfilter-persistent save
```
*(В зависимости от конфигурации дистрибутива, альтернативной командой может служить `sudo iptables-save > /etc/iptables/rules.v4`).*
